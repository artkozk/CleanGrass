достаточно существующего SSH-проброса, а Telegram получает ответы по исходящему HTTPS.

### Сетевой маршрут Telegram на Televibe

На момент переноса DNS выдавал для `api.telegram.org` адрес `149.154.166.110`, соединение
с которым обрывалось за шлюзом хостинга. Локальный firewall контейнера был пуст, а HTTPS
к GitHub и репозиториям Ubuntu работал, поэтому причина не связана с приложением.

В `/etc/hosts` закреплён другой адрес того же официального Telegram API:

```text
149.154.167.220 api.telegram.org # cleangrass-telegram-route
```

Перед закреплением адрес проверен командой `curl --resolve`: соединение прошло с
успешной проверкой TLS-сертификата для `api.telegram.org`. Отдельный VPN не используется,
чтобы бот не зависел от стороннего профиля или домашнего компьютера. Если маршрут когда-то
перестанет работать, сначала нужно проверить `curl -4 https://api.telegram.org`, затем
подобрать доступный официальный адрес с обязательной TLS-проверкой и только после этого
обновить строку с маркером `cleangrass-telegram-route`.

Повторная серия запросов показала, что маршрут к `149.154.167.220` доступен, но отдельное
новое TCP-соединение иногда завершается по таймауту. Поэтому `main.py` включает встроенные
повторы транспорта `telebot`: по умолчанию до пяти попыток, интервал две секунды и таймаут
установки соединения восемь секунд. Параметры можно изменить без правки кода через
`TELEGRAM_MAX_RETRIES`, `TELEGRAM_RETRY_TIMEOUT` и `TELEGRAM_CONNECT_TIMEOUT` в `.env`.
Повторы находятся в общем транспорте, чтобы одинаково работать для polling, ответов на
кнопки и отправки фотографий. Их количество намеренно ограничено: постоянная сетевая
ошибка должна быть заметна в журнале, а обработчик не должен зависать навсегда.

На 21.09.2026 прямой маршрут остаётся нестабильным, поэтому для немедленного восстановления
бота временно используется `TELEGRAM_PROXY=http://127.0.0.1:2099`. Этот loopback-порт
создаётся обратным SSH-туннелем с компьютера администратора к локальному HTTP-proxy Happ.
Порт недоступен извне, а TLS до `api.telegram.org` проверяется самим Telegram-клиентом.
Настройка передаётся прямо в `telebot`, поэтому другие HTTP-запросы сервера через неё не
идут. Это аварийный маршрут: при выключении компьютера туннель исчезнет. После исправления
исходящей сети Televibe нужно выполнить не менее десяти успешных прямых проверок подряд,
удалить `TELEGRAM_PROXY` из `.env`, перезапустить `cleangrass-bot` и убедиться, что polling
работает без новых `ConnectTimeout`.

Файловый журнал использует форматтер `_SecretRedactingFormatter`. Он заменяет полный
`BOT_TOKEN` на `{BOT_TOKEN}` даже внутри traceback сетевой библиотеки. Это необходимо,
потому что исключения `requests` содержат URL Bot API, а токен входит в этот URL. Права
`bot.log` должны оставаться `0600`; старые строки с токеном после внедрения форматтера
санитизируются на сервере без удаления остального журнала.

### Состав текущего переноса

На новый сервер переносится Telegram-органайзер `cleangrass-bot` вместе с последней
SQLite-базой. MAX-бот, API сайта, nginx и сам сайт этим переносом не запускаются: для MAX
нет боевого `MAX_TOKEN`, а домен и TLS сайта не были переданы для переключения. Такое
разделение не мешает Telegram-боту: его учёт, фотографии, напоминания и администраторы
хранятся в импортированной базе и работают автономно.

Исходное описание Timeweb ниже сохранено как историческая схема. Оно необходимо для
понимания старых интеграций и возможного отдельного переноса сайта/MAX, но больше не
указывает место запуска Telegram-органайзера.

Сервер: Timeweb, `root@85.198.82.221` (вход по SSH-ключу).
Всё живёт в `/opt/cleangrass` (код ботов + база) и `/opt/pokos-site` (сайт).

## Компоненты

| Что | Файл | Сервис systemd | Порт |
|---|---|---|---|
| Telegram-бот (органайзер + админка заявок) | `main.py` (+ `requests_admin.py`) | `cleangrass-bot` | — (polling) |
| MAX-бот «Покос 48» для клиентов | `max_bot.py` | `pokos-max-bot` | — (polling) |
| API заявок с сайта | `site_api.py` | `pokos-site-api` | 127.0.0.1:8091 |
| Сайт pokos48.ru | `/opt/pokos-site/` | nginx (конфиг `pokos48`) | 80→443 |

- База — SQLite `/opt/cleangrass/grass_orders.db`, общая для всех трёх процессов.
- Токены — в `/opt/cleangrass/.env`: `BOT_TOKEN` (Telegram), `MAX_TOKEN` (MAX), в git не попадают.
- SSL — Let's Encrypt, автопродление через `certbot.timer`.
- Бэкап базы — ежедневно в `DIGEST_HOUR` Telegram-бот шлёт файл базы админу (внутри `main.py`).

## Таблицы заявок (создаются автоматически)

- `site_requests` — разовые заявки (сайт + MAX): name, phone, address, kind (`pokos`/`zamer`), source (`site`/`max`), status (`new`/`taken`/`rejected`), max_user_id.
- `subscriptions` — регулярка: status `pending` → (админ подтверждает в TG, задаёт дату) → `active`; `declined`/`cancelled`. next_date двигается на interval_days (14) автоматически.
- `max_clients`, `max_addresses` — память MAX-бота: телефон и адреса клиента.

## Потоки заявок

1. Сайт: форма → POST `/api/request` (nginx → 8091) → site_requests + карточка в TG с кнопками.
2. MAX: кнопки бота → site_requests/subscriptions + карточка в TG.
3. Регулярка: карточка «Подтвердить/Отклонить» → дата первого покоса → напоминания
   накануне в 18:00 МСК клиенту (MAX) и админу (TG) — поток `reminder_loop` в `max_bot.py`.

## Антиспам

- site_api: лимит 5 заявок/час с IP, honeypot-поле `website`, дедуп по телефону за 30 минут.
- max_bot: максимум 3 заявки в сутки на клиента, дедуп одинаковых необработанных заявок,
  пересылка свободных сообщений в TG — не больше 5 в час с человека.

## Команды администратора (в Telegram-боте)

- `/zayavki` — необработанные заявки с кнопками «Взял в работу / Отклонить».
- `/subs` — все регулярки со статусами и кнопками.

## Изменение карточек и напоминаний от 27.08.2026

В таблицу `sites` добавлены два совместимых с существующей базой поля:

- `hidden_from_browse INTEGER NOT NULL DEFAULT 0` — скрывает служебную запись только из
  админского слайдера и поиска, не удаляя её заказы из финансового учёта;
- `remind_disabled INTEGER NOT NULL DEFAULT 0` — явно отключает повторные напоминания
  без фиктивной даты окончания.

Миграция схемы выполняется конструктором `Database` через `ALTER TABLE ... ADD COLUMN`.
Все старые строки получают безопасное значение `0`, поэтому до отдельной настройки их
поведение не меняется. `Фантомный заказ` после миграции нужно пометить двумя флагами:
скрыть из листания и отключить его напоминания, так как запись существует только для
учёта. Сам заказ и сумма при этом остаются в базе.

Напоминания из кнопки меню и утреннего дайджеста теперь вызывают общий отправитель
фотокарточек. Он использует превью участка из `service_photos`; при отсутствии фото или
ошибке Telegram отправляется текстовый fallback и пишется ошибка с `site_id`. Общий
отправитель нужен, чтобы ручной и автоматический потоки не расходились по поведению.

### Безопасный порядок развёртывания

1. Проверить `git status` и сохранить незакоммиченные боевые изменения отдельным коммитом.
2. Сделать SQLite-бэкап через API SQLite, а не копированием открытого файла.
3. Скопировать изменённые Python-файлы в `/opt/cleangrass`.
4. Запустить `.venv/bin/python test_logic.py` и `py_compile` до перезапуска сервиса.
5. Инициализировать `Database('grass_orders.db')`, чтобы добавить новые колонки.
6. Найти служебную запись по точному адресу `Фантомный заказ`, убедиться, что она одна,
   затем установить ей `hidden_from_browse=1` и `remind_disabled=1`.
7. Перезапустить только `cleangrass-bot`; MAX-бот и API не используют изменённый поток.
8. Проверить `systemctl is-active cleangrass-bot`, свежий журнал и запрос к базе: обычные
   просроченные участки должны иметь фото, а служебная запись — оба флага со значением `1`.

### Откат

Код можно вернуть на предыдущий Git-коммит и снова перезапустить `cleangrass-bot`. Новые
колонки удалять при откате не нужно: старая версия их игнорирует, а удаление потребовало
бы перестройки SQLite-таблицы и создало бы лишний риск. Если требуется отменить только
настройку данных, достаточно выставить соответствующему участку
`hidden_from_browse=0, remind_disabled=0`; история заказов при этом не затрагивается.

## Эксплуатация нового Telegram-прода

Версионируемый unit находится в `deploy/cleangrass-bot.service`. При изменении unit-файла
его копируют в `/etc/systemd/system/cleangrass-bot.service`, выполняют
`systemctl daemon-reload` и только затем перезапускают сервис. Unit имеет автоматический
рестарт, приватный `/tmp`, запрещает получение новых привилегий и разрешает запись только
в `/opt/cleangrass`; это оставляет SQLite и ежедневный временный бэкап рабочими, но
ограничивает последствия ошибки процесса.

Проверка после каждого развёртывания:

```sh
cd /opt/cleangrass
.venv/bin/python test_logic.py
.venv/bin/python -m py_compile config.py database.py keyboards.py main.py money.py requests_admin.py states.py
sqlite3 grass_orders.db 'PRAGMA integrity_check;'
systemctl restart cleangrass-bot
systemctl is-active cleangrass-bot
journalctl -u cleangrass-bot -n 100 --no-pager
```

В журнале должна появиться строка `Bot running...`, после которой не должно быть ошибок
`409 Conflict`, `ConnectionError` или циклических рестартов. Через Bot API дополнительно
проверяются `getMe` и уменьшение `pending_update_count`. Сам факт состояния `active` не
доказывает работоспособность, если сетевой маршрут Telegram снова недоступен.

Перед заменой базы сервис останавливают, текущую базу сохраняют через SQLite backup API
или команду `.backup`, проверяют SHA-256 и `PRAGMA integrity_check`, и только затем кладут
новый файл. Простое копирование открытой SQLite-базы запрещено, потому что WAL/незавершённая
транзакция могут дать внешне существующий, но неполный файл.

Для отката переноса достаточно остановить `cleangrass-bot`, вернуть проверенный файл из
`/var/backups/cleangrass`, снова выполнить `PRAGMA integrity_check` и запустить сервис.
Строку `/etc/hosts` нельзя удалять до подтверждения прямого доступа к адресу, который
возвращает DNS: без этого процесс останется `active`, но перестанет отвечать Telegram.
